# 公開海流マップの実装記録

## 実予報との接続と公開境界（2026-11-21）

承認済みの紺・金の意匠、原図地形、島沿いの粒子表示を本サイトへ組み込んだ。
流速スケールは0〜6kt。数値は上限で切らず、色・尾長だけを6ktで飽和させる。
海流の日付・8〜14時の選択は、旧ハンマー予報の時系列から独立している。

入力は[Open-Meteo Marine API](https://open-meteo.com/en/docs/marine-weather-api)の
`models=meteofrance_currents`、`wind_speed_unit=kmh`、`timezone=Asia/Tokyo`。
取得した10日240時間のうち、初回は225時間が有効、末尾15時間はnullだった。
要求点34.5717/138.9433、返却格子中心34.541664/138.95836。
初回取得は2026-11-21 03:37 JST、最後の有効対象時刻は11月30日08:00 JST。
初回流速は0.2〜3.6km/hであり、6ktの表示対応を実際の6kt予報と取り違えない。

[Copernicus Marine SMOC](https://documentation.marine.copernicus.eu/PUM/CMEMS-GLO-PUM-001-024.pdf)は
広域の海面総流で、潮汐・波浪を独自に再加算しない。モデル発表時刻はAPIレスポンスから不明。
取得日時と発表日時を同一視せず、画面で不明と明記する。
取得から36時間の期限と48時間先までの有効対象範囲を検査するが、これは入力の運用検査であり、
供給元モデルの毎回の更新や予報精度を証明するものではない。

`ocean-map.yml`は既存full予報の公開前検査を解除せず、独立した海流の検査と公開を行う。
旧予報の内容は既存発表記録のハッシュと一致しなければ海流専用経路で公開できない。
古いハンマー予報・長期カレンダーは閲覧時に表示を停止する。
海流公開だけでハンマーの新しい発表記録を保存しない。

Claude Codeのアカウント認証によるレビューを受け、未公開予報の混入防止、取得とモデル時刻の区別、
欠測ペア・時刻変換、任意方位の検査を確認した。別担当レビューで日付跨ぎ時の長期表示と
二つのActionsのcheckout対象を修正した。

受入検査はPython36件、Node17件が成功。実ブラウザでPC、390px、320px幅を確認し、
日付・時刻切替、広域/模式切替、予報末尾の部分欠測、欠測時の数値・粒子停止、
旧予報・カレンダーの失効非表示を確認。横あふれ・実行エラーなし。
これらは実装・表示の検査であり、現地の海中流速や遭遇確率の精度検証ではない。

## 模式方向場の再生成

`analysis/map_field/` は、公開用の地形から模式方向場を再生成するオフライン用パッケージ。
毎朝の予報・ビルドでは既成の `engine/map_flow_field.json` を読み込むだけで、NumPy/OpenCV を要求しない。
通常の `requirements.txt` や daily workflow に、この再生成環境の依存を追加しない。

| ファイル | 用途 |
|---|---|
| `map_field/generate-current-field.py` | 露出輪郭の幾何、調和流れ関数の解法、海岸補正、粒子・線分検証。単独起動は旧3方向の比較用データを生成する |
| `map_field/generate-current-field-any-direction.py` | 公開用の未正規化2基底を生成するCLI。公開資産はこちらを使用する |
| `map_field/trace_source.py` | 公開トレースの露出部だけを、絶対 `M/L/Z` パスから点列へ復元する標準ライブラリのみの読込処理 |
| `map_field/manifest.json` | 承認済み露出点列・基底bytes・scale・入力識別子の照合値 |
| `map_field/requirements.txt` | 再生成時だけ使う固定バージョンの依存 |

元PNG、元PNGへのローカルパス、点描、深度、未閉鎖の根の輪郭は再生成入力に含めない。
入力は `engine/map_trace.json` の `kind=exposed` かつ閉じた17輪郭。
露出輪郭は合計562点で、公開パスから復元した点の順序・値が初回計算入力と完全に一致することを確認した。
水中根は遮蔽物にせず、海底水深から局所流速を計算しない。

### 入力と基底だけを照合する

リポジトリルートから次を実行する。この確認はNumPy/OpenCVのないPythonでも動作する。

```sh
python analysis/map_field/generate-current-field-any-direction.py --check-source
```

公開トレースの識別子、17露出輪郭の点列ダイジェスト、現行基底の復号bytesとscaleを照合する。
`source.traceSha256` は公開トレースの **`source.sha256` を引き継ぐ**。
これは承認済み正本トレースの識別子であり、コンパクトJSONファイル自体のハッシュへ置き換えない。
新たな出力には、コンパクトJSONファイルと再生成スクリプトのハッシュを別項目として記録する。

### 同じ基底を再生成する

初回計算環境はPython 3.12、NumPy 2.3.5、opencv-python-headless 5.1.0.95。
以下はWindowsの例。macOS/Linuxでは仮想環境内のPythonを `.venv/bin/python` に読み替える。

```sh
python -m venv analysis/map_field/.venv
analysis/map_field/.venv/Scripts/python.exe -m pip install -r analysis/map_field/requirements.txt
analysis/map_field/.venv/Scripts/python.exe analysis/map_field/generate-current-field-any-direction.py --verify-basis --output analysis/map_field/map_flow_field.generated.json
```

再生成は24方位の検証まで実行し、`--verify-basis` により既存の
`engine/map_flow_field.json` と `fields.ne` / `fields.west` のbytes・scale・encodingが同一か確認する。
`--trace`、`--reference`、`--output` で入力・比較先・出力先を指定できる。
既定出力は `analysis/map_field/map_flow_field.generated.json` で、`engine/` の資産を自動上書きしない。
スクリプト名や来歴のハッシュは移植に伴い変わるため、JSON全体のbytes一致を判定条件にはしない。

地形を変更する場合は新たな承認と入力識別子・manifestの更新を行い、全方位検証を再実行する。
未確認のパス形式を黙って近似せず、`M/L/Z` 以外の露出パスは読込エラーにする。
初回再生成を済ませた後も、基底のノルムを地点別ktとして使用してはならない。

## 計算条件

- 原図座標：921×1356px、右が+x、下が+y。GPS・真方位・水深の校正は行っていない。
- 格子：原点(0,0)、6px間隔、155×227点。右端の格子点はx=924。
- 表示範囲：viewBox `[165,270,756,1086]`。流れの描画は `[165,510,756,846]` に限定。
- 露出部：17閉輪郭をそのまま使用。解法上の9px離隔と格子化により13成分となる。
  この離隔は画面上の侵入防止であり、実在する岩や水路の形を変更した測量結果ではない。
- 外側境界：NE=(1/√2,−1/√2)、West=(−1,0)の一様流を与える。
- 島境界：各独立成分に別々の流れ関数定数を持たせ、隣接海セル平均へ更新して離散的な循環ゼロ条件へ近づける。
  全島を同じ定数にはしない。
- 解法：赤黒SOR、緩和係数1.91、50反復ごとに残差を確認。
  調和式残差・浮動境界残差がともに0.0002未満で終了し、最大12,000反復。
- 海岸補正：原輪郭の最近接法線に対する固定の線形接線投影。
  18px以下で全補正、18〜72pxで滑らかに減らし、72px以遠は補正しない。
- 基底の各ノードを正規化しない。signed int16 little-endianのu/v交互列をBase64化し、場ごとのscaleで復号する。
- 水中根・深度・気温・水温・ライブ予報値は基底生成の入力にしない。

予報のTOWARD方向を原図の北から時計回りの角度θとして、次の係数で2基底を合成する。

```text
a = sqrt(2) * cos(theta)
b = cos(theta) - sin(theta)
F = a * F_NE + b * F_West
```

方向更新時に全ノードの合成場をキャッシュしても、先に2基底を同じ位置で双線形補間してから合成しても同値。
合成後のサンプルだけを正規化する。ノルム0.025未満は停留点扱い。
45°はNE、225°はその反転、270°はWestとなる。
0〜6ktの表示値は広域予報の一値から色・尾長・演出速度へ一律に反映し、`|F|` からktを導かない。
接線補正と表示方向への正規化後の場について、実際の海流の質量保存や局所速度を保証しない。

## 検証結果と限界

公開基底を作成した初回の検証結果は `engine/map_flow_field.json` の `validation` に保持している。

| 項目 | 結果 |
|---|---:|
| 方位 | 0〜345°を15°刻み、24方位 |
| 初期サンプル | 各700点（陸内31点を除外。初期停留点も方位別に除外） |
| RK2検証刻み | 原図2px、各初期点で最大700ステップ |
| 検査した線分 | 2,945,631本 |
| 17露出輪郭との交差 | 0本（描画マスクで隠す前の試行経路を検査） |
| 原輪郭までの最短距離 | 3.811px |
| 外側角点の方向ベクトル誤差 | 全24方位で0.000169未満 |
| NE解の反復数・最大調和残差 | 1,150回・0.00017550 |
| West解の反復数・最大調和残差 | 1,200回・0.00017034 |

画面側はRK2の移動を1サブステップ1.8px以下とし、正確な露出パスと北側境界で、粒子の頭・尾・描画端までマスクする。
停留点に達した粒子はフェードして再配置する。正常な画面外退出と停留停止は別に集計する。
格子より細かい角や近接岩では方向の誤差が残るため、数値場だけに侵入防止を任せない。
24方位の検査は全ての連続角度・初期位置を網羅する証明ではなく、実測による局所流の検証でもない。

パッケージ移植時には24方位の全面再計算は繰り返していない。
3本のPythonファイルの構文、公開入力からの17輪郭562点の完全一致、既存基底の復号ハッシュ、
10個の数値処理関数のAST一致を確認した。NumPy/OpenCVを使わない `--check-source` の実行も通過している。
さらに公開パスを入力として2基底だけを再計算し、現行資産のNE/West双方でencoding・scale・Base64 bytesの完全一致を確認した。
この照合では資産ファイルを書き換えていない。
